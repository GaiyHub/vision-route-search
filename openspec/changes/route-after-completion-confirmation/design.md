## Context

`requestCompletionDecision` 当前在完成判定出现时执行四件事：读取当前外部前台包名、发布 `completionPending`、显示通知并把豆泡拉到前台；确认被用户处理或 60 秒超时后，清除确认状态并无条件调用 `returnToPreviousApp`。这保证代操作任务可以回到现场，但纯文本问答也会被切回此前恰好打开的 App。

AgentLoop 已通过 `action` 事件把每次实际工具调用传给 `agentBridge`，宿主也已有 `getCurrentForegroundApp`、`getLastForegroundApp`、`bringHostAppToForeground` 和 `returnToPreviousApp`。因此本变更可以留在宿主编排层，不改变 AgentLoop、工具协议或原生接口。

## Goals / Non-Goals

**Goals:**

- 对每次任务稳定地区分“实际代操作外部手机 UI”和“问答/只读处理”。
- 把完成确认改为“完成”“继续”“补充信息”三个明确决策，并让补充内容进入下一轮 Agent 上下文。
- 完成确认结束后，代操作任务恢复最近操作现场，问答任务保持豆泡在前台。
- 「完成」「继续」「补充信息提交」和超时默认完成使用同一条条件路由规则。
- 回跳失败不阻塞确认 gate、任务继续或任务收尾。
- 任务之间严格重置分类和回跳目标，避免串用上一次任务状态。

**Non-Goals:**

- 不用额外 LLM 请求做意图分类，也不建立中文关键词分类器。
- 不改变 AgentLoop 的 `completionGate?: (result) => Promise<'complete' | { continue: string }>` 协议。
- 不改变高风险 `confirm_action` 的现有回跳行为。
- 不为内置浏览器引入外部 App 回跳；它属于豆泡宿主内的网页能力。
- 不修改 Android 最近任务恢复算法或增加 iOS 实现。

## Decisions

### 1. 以实际工具行为判定，而不是仅分析指令文本

每次 `processCommand` 开始时创建任务级 `TaskInteractionKind`，初值为 `question_answer`。当 bridge 消费到以下任一外部手机 UI 操作工具的 `action` 事件时，单向升级为 `device_operation`：

- 点击与输入：`tap`、`long_press`、`type_text`、`clear_text`、`press_enter`、`set_checked`
- 手势：`swipe`、`scroll`、`scroll_until_found`
- 应用/系统导航：`open_app`、`global_action`

别名先按现有规范名规则归一化。一次真实调用即算代操作证据，即使结果失败；“用户要求代操作但第一次动作失败”仍应在确认后回到操作现场。分类是单向的：任务一旦发生外部操作，本任务后续的回答不会把它降回问答。

以下调用不升级：只读观察/查找工具、等待、Todo、笔记、技能、确认与终止工具，以及全部 `browser_use` 子动作。内置浏览器即使导航或点击也在豆泡自己的 WebView 内完成，完成时应留在豆泡。

备选方案一是用关键词或再发一次 LLM 请求判断用户意图。前者对自然语言和混合任务脆弱，后者增加延迟、Token 和不确定性，因此不采用。备选方案二是只看确认框弹出时的前台包名；用户可从外部 App 发起纯问答，这会重现当前误跳，因此也不采用。

### 2. 在宿主侧增加纯策略函数和任务级状态

新增一个无 React Native 依赖的宿主策略模块，集中维护：

- `TaskInteractionKind = 'question_answer' | 'device_operation'`
- 外部操作工具集合与规范名归一化
- `nextInteractionKind(current, toolCall)` 单向状态转换
- `shouldReturnToExternalApp(kind)` 回跳决策

`agentBridge` 只持有当前任务的一个状态值：在 `processCommand` 开始前重置，在收到 action 事件时更新，在 finally 中清除。纯函数可直接单测，也避免把分类规则散落在完成 gate 和 UI 中。此状态不需要持久化或暴露给设置页，因为它只在一次运行内有效。

### 3. 完成确认框采用三选项状态机

确认状态分为两个 UI 阶段：

- `decision`：展示任务、模型判定以及“完成”“继续”“补充信息”。
- `supplement`：展示同一上下文和多行输入框，提供“返回”与“提交并继续”。

三个入口的语义为：

- “完成” → resolver 接收 `'complete'`。
- “继续” → resolver 接收 `{ continue: '用户确认任务尚未完成：<模型判定>。请继续完成剩余步骤。' }`。
- “补充信息” → 仅进入 `supplement`，不调用 resolver；用户提交后 resolver 接收 `{ continue: '用户确认任务尚未完成，并补充以下信息：<用户输入>。请结合补充信息继续完成剩余步骤。' }`。

补充内容先 trim，空白内容禁止提交；长度上限为 2000 个字符并在 UI 显示计数，防止意外把超长文本注入下一轮 Prompt。草稿只保存在 Modal 本地状态，不进入日志、通知或持久化设置；确认结束、任务停止或 pending 结果变化时清空。

点击“返回”只退出补充输入态并回到三选项，不代表继续或完成。Android 返回键在补充态等同“返回”，在决策态不得静默映射成“完成”。

现有系统通知继续作为后台兜底，提供“完成/继续”两个直接动作；补充信息需要点击通知进入豆泡后在 Modal 内填写，避免在本变更中引入 RemoteInput 和敏感文本广播。

### 4. 补充输入期间暂停自动完成超时

决策态保留现有 60 秒无响应默认完成。用户主动选择“补充信息”后，已经明确表示任务未完成，因此必须暂停该轮 JS timer 和 freeze-safe timer 的结算资格；旧异步 timer 即使返回也通过 gate generation 检查失效，不能把正在编辑的任务判为完成。

用户从补充态返回三选项时重新开始一个完整 60 秒决策计时。用户提交、选择完成/继续或停止任务后清除所有有效计时状态。这样既满足“提交后才继续”，也保留未开始交互时的防悬挂策略。

备选方案是让原 60 秒计时在用户输入时继续运行，但可能在编辑中突然完成任务，因此不采用。另一个方案是补充态也设置超时并自动继续，这会在没有有效补充内容时违背用户选择，也不采用。

### 5. 回跳发生在确认 gate 被真正处理之后

确认框出现时仍先把豆泡拉到前台，让用户能看到并操作 Modal；不能在弹框后立即切走。`settle` 在清理通知与 `completionPending` 后读取当前任务分类：

- `device_operation`：异步恢复本轮 gate 打开前捕获的外部 App。
- `question_answer`：不调用任何回跳 API，豆泡保持前台。

该规则覆盖“完成”“继续”“补充信息提交”以及 60 秒超时。进入补充输入态不算 settle，不清除确认状态，也不触发回跳。代操作任务选择“继续”或提交补充信息后先恢复现场，再让 AgentLoop 继续；问答任务则留在豆泡继续生成。

分类必须在每次 gate 处理时读取，而不是在任务开始时复制。这样问答任务被判“未完成”后若继续阶段实际执行了外部操作，下一次完成确认会按代操作路由。

### 6. 每轮 gate 重新捕获目标，最近记录只作后备

只有 `device_operation` 需要捕获回跳目标。首选 gate 打开瞬间的 `getCurrentForegroundApp`，因为它最接近 Agent 最后操作的页面；若为空，再读取 `getLastForegroundApp`。目标必须非空且不能是豆泡自身包名，之后才调用 `returnToPreviousApp`。

每次完成判定重新捕获，不复用前一轮目标。回跳采用 fire-and-forget/best-effort；失败仅写入不含页面内容的诊断日志，不得阻塞 resolver、继续执行或完成收尾。

### 7. 自动化以策略、bridge 和确认框状态测试为主

纯策略测试覆盖全部外部操作工具、非操作工具、别名、单向升级和任务重置。bridge 测试 mock 原生控制器，验证两类任务在完成、继续、补充提交和超时路径上的调用差异、目标后备及异常降级。确认框测试覆盖阶段切换、空值/长度校验、草稿清理和补充态 timeout generation 失效。真机 ADB 再验证 MIUI 上的前台实际结果。

## Risks / Trade-offs

- [用户发出代操作意图，但 Agent 在任何外部动作前就直接宣告完成] → 按实际行为会归为问答并留在豆泡；这是避免自然语言误判的保守选择，确认后若需要可再增加显式任务类型信号。
- [只读屏幕查询也来自外部 App] → 不回跳是有意行为：用户需要在豆泡查看答案，而非继续操作现场。
- [新增或自定义工具能操作外部 UI，但未加入分类表] → 默认不回跳以避免意外切换；新增外部 UI 工具时必须同步策略测试和工具集合。
- [gate 打开前已经回到豆泡，当前包名为空] → 使用无障碍服务记录的最近外部 App 作后备，并排除宿主包名。
- [MIUI 阻止回跳或最近任务卡失效] → 保持 best-effort；确认流程照常完成，用户仍可手动切换。
- [通知按钮处理时 JS/宿主前台状态不同] → 所有确认入口共用同一个 `settle` 和条件路由，避免入口间行为分叉。
- [用户进入补充态后长期不提交导致任务悬挂] → 这是用户主动选择后的预期暂停；保留“返回”“完成”“继续”和停止任务等明确出口，不自动丢弃草稿或擅自继续。
- [补充内容过长增加 Prompt Token 或包含敏感信息] → 限制 2000 字符，只注入当前任务下一轮上下文，不写任务诊断日志和系统通知。
- [不可取消的 freeze-safe promise 在补充态结束后误结算] → 每轮 timeout 使用递增 generation，只有当前决策态 generation 可以 settle。

## Migration Plan

1. 先增加纯策略模块和单元测试，不接入运行路径。
2. 在 `processCommand` 生命周期和 action 事件消费处维护任务分类。
3. 扩展完成确认状态和 Modal，接入三选项、补充输入校验及 generation 化超时控制。
4. 将完成 gate 的无条件回跳替换为按分类回跳，并加入目标后备和诊断日志。
5. 运行相关 Jest、完整 TypeScript typecheck，再构建 APK 并通过 ADB 分别验证代操作、问答和补充信息继续执行。
6. 若真机出现问题，可分别回滚三选项 UI 或条件路由接入；没有持久化迁移或原生 API 变更。

## Open Questions

- 本设计把“代操作”定义为本任务实际调用过外部 UI 变更工具，而不是仅依据用户句子的语义。若产品期望“只要用户表达了操作意图，即使一个动作都没执行也要回跳”，实施前需要增加显式意图分类机制。
- 当前建议内置 `browser_use` 始终归入问答/宿主内处理；若未来浏览器独立成外部 Activity，应重新归类。
